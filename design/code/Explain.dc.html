New concept · Cleaning up an async effect
How to hold it
A cleanup function cannot cancel a promise — nothing in JavaScript can. What it can do is make the result irrelevant. That is the entire idea, and it is why the pattern always looks like a flag rather than an abort.

A
Declared inside the effect, so each run gets its own flag. A module-level flag would be shared by every mount at once.
B
The fetch still finishes and still costs you the request. You are only refusing to act on it.
C
Runs before the next effect and on unmount. This is the only line that closes over the flag from the outside.
Without it
−
fetchUser(userId).then(setUser);
+
fetchUser(userId).then((u) => { if (!cancelled) setUser(u); });
What the removed line actually did
$ npm run dev — open /users/7, then /users/9 fast
Warning: state updated on an unmounted component.
… and the page shows user 7 after you asked for 9.
That second line is the one that bites in production: not a crash, just the wrong user on screen, whenever the first request happens to be slower than the second.

The rule that keeps this from becoming a tutorial
One listing, at most twelve lines, at most three annotations. The learner reads this once, for ninety seconds, before being asked to reproduce it from memory. A page of code is a page they will skim — and skimming is the failure mode this whole product exists to beat.
What the two teach modes do differently
example_first shows this card, then asks. try_first shows the diff’s minus line only and asks what goes wrong, then reveals the rest of the card. Same blocks, different order — which is the point of storing them as an array.
